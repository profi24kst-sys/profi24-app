# Stage B.2 — филиалы, деньги и материальная ответственность

## Цель
Не допустить, чтобы права роли сами по себе давали сотруднику доступ к чужим деньгам, складу или заказам другого филиала. Авторизация строится как `роль + филиал + ответственный + состояние документа`.

## Филиалы
- `branches` — справочник филиалов; первый рабочий филиал `KST / Костанай`.
- `users.primary_branch_id` — основной филиал сотрудника.
- `user_branches` — дополнительные филиалы; у сотрудника только один основной.
- `requests.branch_id` — обязательный филиал заказа.
- существующие данные безопасно мигрируются в Костанай.
- обычное создание заказа наследует основной филиал ответственного менеджера; БД не допускает назначение инженера из другого филиала.
- менеджер получает доступ только к заказам своих филиалов.
- инженер может быть назначен только в филиал, членом которого он является.
- изменение состава филиалов и основной точки пишется в неизменяемый аудит.
- OWNER / SUPERVISOR имеют глобальный операционный обзор; ACCOUNTANT — глобальный учётный обзор; MANAGER ограничен `user_branches`.

## Филиальная изоляция списков и агрегатов
Ограничение применяется не только к `GET /requests/:id`, но и к агрегатам. Для MANAGER по его филиалам пересчитываются/фильтруются:
- список заказов;
- показатели клиента `request_count` и `lifetime_paid`;
- рекламации;
- диспетчерские контроли;
- операционный dashboard;
- финансовый dashboard.

Это исключает утечку чужих заказов и чужой выручки через списки и сводные показатели даже при запрете прямого открытия заказа.

## Кассы и счета
- `finance_accounts.branch_id` — принадлежность денежного счёта филиалу.
- при нескольких активных филиалах `branch_id` при создании денежного счёта обязателен.
- ответственный сотрудник должен относиться к филиалу счёта.
- менеджер может проводить операции только по своему ответственному счёту и только в доступном филиале.
- бухгалтер и собственник имеют финансовый административный контур.
- управляющий имеет просмотр и read-only аудит, но не финансовые корректировки/сторно/возвраты.
- бухгалтер может принять оплату и оформить документированный возврат; общий order guard не превращает это право в техническое право ремонта.
- инженер и стажёр не имеют глобального `finance.view`; узкие расходы/покупки по своему заказу проверяются отдельно через `requireOrder + lockAccounts`.

## Кассовые смены
- смена открывается только по активному `CASH` счёту;
- одновременно по кассе может быть только одна открытая смена;
- сохраняются книжный и фактический остаток на открытии;
- рассчитывается расхождение на открытии;
- наличные движения автоматически связываются с открытой сменой;
- при закрытии фиксируются ожидаемый и фактический остатки и variance;
- закрытая смена и журнал событий неизменяемы;
- расхождение создаёт управленческий контроль.

## Склад
- каждая `warehouse_items` принадлежит конкретному филиалу;
- филиал позиции нельзя менять обычным PATCH;
- выдача инженеру разрешена только если инженер относится к филиалу склада;
- стажёр не может быть материально ответственным получателем запчасти;
- установка в заказ разрешена только со склада филиала заказа;
- резервы также обязаны совпадать с филиалом заказа;
- проведённые складские движения неизменяемы.

## Межфилиальные перемещения
Перемещение — отдельный документ `warehouse_transfers`, а не корректировка остатка:
1. проверяется доступ к исходному и целевому филиалу;
2. блокируется исходный остаток;
3. создаётся/находится позиция назначения;
4. создаются `TRANSFER_OUT` и `TRANSFER_IN`;
5. сохраняются причина, документ и автор;
6. документ и движения нельзя переписать задним числом.

## Закупки и запчасти
- `purchase_orders.branch_id` обязателен;
- позиция заказа поставщику должна быть со склада того же филиала;
- минимальные остатки и резервы фильтруются по доступным филиалам;
- диагностический поиск запчастей ограничен филиалом текущего заказа;
- `part_demands` и `special_part_orders` наследуют филиал заказа;
- спецзаказ приходуется только на склад филиала заказа;
- автоматическое возобновление ремонта не смешивает остатки разных филиалов.

## RBAC поверх филиального контура
- OWNER — глобально, все документированные операции.
- SUPERVISOR — глобальная операционка, филиалы, склад, закупки; finance view/audit без корректировок и возвратов.
- ACCOUNTANT — глобальные финансы, оплаты/возвраты, кассы, read-only склад/закупки, payroll; без диагностики/работ ремонта.
- MANAGER — только доступные филиалы; свои ответственные денежные источники; склад receive/issue без writeoff; закупки.
- ENGINEER — только назначенные/участвуемые заказы; нет глобальных финансов/склада; материальная ответственность отражается по выданным движениям.
- TRAINEE — только участие у активного наставника; комментарии/файлы; не получает самостоятельную кассу или складскую ответственность.

## Автоматическая HTTP-приёмка шести ролей
`server/test/role-http-acceptance.test.js` запускает реальные Fastify route handlers поверх PGlite и проверяет положительные и отрицательные сценарии для всех шести ролей:
- OWNER — критические операции;
- SUPERVISOR — операционное управление + финансовый аудит без корректировки денег;
- ACCOUNTANT — оплата/возврат без технического ремонта;
- MANAGER — свой филиал и собственная касса;
- ENGINEER — только технический контур доступных заказов;
- TRAINEE — только участие у наставника, комментарии/файлы.

`server/test/manager-branch-http.test.js` отдельно проверяет отсутствие чужого филиала в списках, рекламациях, диспетчерском контроле, клиентских агрегатах и dashboard.

## Инварианты при приёмке
- чужой филиал нельзя обойти прямым API-вызовом или агрегатным endpoint;
- чужую кассу нельзя использовать, даже зная `account_id`;
- складскую позицию нельзя скрыто перепривязать к другому филиалу;
- деталь другого филиала нельзя зарезервировать или установить в заказ;
- стажёра нельзя сделать основным инженером или материально ответственным получателем;
- проведённые деньги, кассовые смены, складские движения и межфилиальные документы не редактируются задним числом;
- возврат оплаты связан с исходной оплатой и требует документ/причину;
- все старые данные после миграции остаются доступными и не теряют историю.
