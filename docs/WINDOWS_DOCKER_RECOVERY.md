# PROFI24 CRM — безопасное восстановление Docker на Windows

Этот сценарий предназначен для локальной установки PROFI24 CRM в Docker Desktop, когда часть контейнеров красная, `unhealthy`, не запускается из-за старых зависимостей или локальная копия репозитория осталась на старой ветке.

## Главное правило

Сценарий **никогда не выполняет `docker compose down -v` и не удаляет Docker volumes**. PostgreSQL и вложения должны сохраняться.

## Перед запуском

В каталоге CRM должен существовать ваш текущий `.env` с тем же `POSTGRES_PASSWORD`, который использует существующий PostgreSQL volume. Recovery-скрипт специально **не создаёт новый `.env` и не подменяет секреты**.

Если `.env` отсутствует, сценарий завершится до остановки или запуска контейнеров.

## Автоматическое восстановление

Откройте PowerShell в каталоге репозитория и выполните:

```powershell
powershell -ExecutionPolicy Bypass -File .\ops\repair-local.ps1
```

Сценарий последовательно:

1. проверяет Docker Desktop и Git;
2. останавливается, если есть незакоммиченные локальные изменения;
3. переключается на канонический `main` и делает только `git pull --ff-only`;
4. требует существующий `.env` и сохраняет его без изменений;
5. валидирует Docker Compose;
6. удаляет только старые compose-контейнеры и orphan-контейнеры, **без volumes**;
7. запускает PostgreSQL отдельно;
8. проверяет TCP-аутентификацию существующего PostgreSQL volume паролем из `.env`;
9. запускает и проверяет core API;
10. пересобирает и запускает весь CRM stack;
11. проверяет health endpoint каждого CRM-модуля через web/nginx;
12. только после успешной проверки запускает backup worker.

Если какой-либо этап не проходит, сценарий выводит состояние контейнеров и логи проблемных сервисов и прекращает работу без удаления данных.

## Только диагностика

Чтобы ничего не менять и только получить состояние и логи:

```powershell
powershell -ExecutionPolicy Bypass -File .\ops\repair-local.ps1 -DiagnoseOnly
```

## Частая причина: старый PostgreSQL volume и новый пароль

`POSTGRES_PASSWORD` используется образом PostgreSQL только при первоначальном создании пустого volume. Если позже изменить пароль в `.env`, существующая БД автоматически не сменит пароль.

`repair-local.ps1` специально проверяет реальную TCP-аутентификацию до запуска всего стека. При несовпадении он останавливается с сообщением и **не пересоздаёт БД**.

В таком случае нельзя удалять volume. Нужно либо вернуть в `.env` пароль, с которым volume был создан, либо выполнить контролируемое восстановление в новый volume из проверенного backup-set по `docs/PRODUCTION_RUNBOOK.md`.

## Что нельзя делать для «починки»

Не используйте без подтверждённого резервного копирования:

```powershell
docker compose down -v
docker volume prune
docker system prune --volumes
```

Эти команды могут удалить рабочую базу или другие persistent volumes.

## Критерий успешного локального запуска

В конце сценарий должен вывести:

```text
PROFI24 CRM local recovery completed successfully.
```

и все обязательные health endpoints должны отвечать через `http://127.0.0.1:<WEB_PORT>`.

Production-развёртывание остаётся отдельной процедурой: используйте `ops/start-production.sh` и `docs/PRODUCTION_RUNBOOK.md`, а не локальный recovery-скрипт.
