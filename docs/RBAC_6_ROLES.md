# PROFI24 CRM — RBAC: 6 ролей

Статус: Stage B, production-oriented RBAC foundation.

## Роли

| Код | Название | Назначение |
|---|---|---|
| `OWNER` | Собственник | Полный контроль, критические действия, роли, финансы и аудит |
| `SUPERVISOR` | Управляющий | Полная операционная работа сервиса без системных/владельческих исключений |
| `ACCOUNTANT` | Бухгалтер | Финансы, возвраты/корректировки, аудит, зарплата; без технических изменений ремонта |
| `MANAGER` | Менеджер | Приём и ведение заказов, диспетчеризация, коммуникации, платежи, склад/закупки в операционных пределах |
| `ENGINEER` | Инженер | Только назначенные заказы и технические действия по ним |
| `TRAINEE` | Стажёр | Только заказы своего наставника, где он добавлен участником; комментарии и файлы без самостоятельной ответственности |

## Основная модель доступа

Backend является источником истины. Скрытие кнопки во frontend не считается авторизацией.

- `OWNER`, `SUPERVISOR`, `ACCOUNTANT`, `MANAGER` имеют доступ ко всем заказам в рамках своих permissions.
- `ENGINEER` видит только заказы, где он указан как основной `requests.engineer_id`.
- `TRAINEE` не может быть основным инженером заказа.
- Для стажёра используется `user_mentors` + `request_participants`.
- Стажёр видит заказ только если:
  1. он добавлен в `request_participants` как `TRAINEE`;
  2. его текущий активный наставник имеет роль `ENGINEER`;
  3. основной инженер заказа совпадает с этим наставником.
- При смене наставника старый доступ стажёра перестаёт действовать автоматически.

## Frontend

Новые и мигрированные UI-модули должны использовать:

```js
window.Profi24RBAC.can(window.Profi24RBAC.P.<PERMISSION>)
```

Нельзя считать проверку вида `role === 'OWNER'` или `['OWNER','MANAGER'].includes(role)` достаточной архитектурой для нового кода.

`rbac-ui-v2.js` остаётся слоем совместимости для старого `app3.jsx` до полной миграции legacy UI.

## Защита заказов

`server/src/access.js` выполняет:

1. повторную загрузку активного пользователя из БД после JWT;
2. проверку известной роли;
3. проверку scope заказа;
4. проверку допустимости мутации по роли/маршруту;
5. запрет обычных мутаций закрытого/отменённого заказа;
6. проверку дочерних ресурсов через `request_id`.

## Тестирование

`npm run test:crm` включает RBAC regression tests. Минимальная приёмка Stage B:

- БД принимает только шесть ролей;
- unknown role отвергается;
- бухгалтер не может менять диагноз/работы;
- инженер не может принимать оплату, менять расписание, закрывать/отменять заказ;
- стажёр может писать заметки/добавлять допустимые файлы, но не менять ремонт;
- стажёр не получает доступ без активного наставника и участия в заказе;
- стажёр теряет доступ после смены наставника;
- закупки разделены на view/manage;
- CI: backend syntax, finance tests, CRM/RBAC regression, web build, Docker compose/build и smoke должны быть зелёными.
