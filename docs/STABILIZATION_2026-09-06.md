# Стабилизация CRM — 6 сентября 2026

Первый этап исправлений после проверки CRM по ТЗ. Это описание выполненного этапа, а не заключение о полной готовности системы.

## Изменения

- Общая авторизация проверяет активность пользователя и текущую роль в БД при каждом запросе. Блокировка и смена роли действуют и на ранее выданный токен.
- Проверяется доступ инженера к назначенному заказу, включая дочерние строки диагностики, файлы, согласования и сообщения. Списки клиентов и техники ограничены связанными заказами.
- Обычное изменение закрытого или отменённого заказа блокируется в API и триггерами БД. Защищены работы, детали, платежи, диагностика, завершение, вложения и подписи. Остаются документированные возвраты и открытие закрытого заказа собственником с причиной; комментарии можно дописывать.
- Выдача и списание со склада учитывают активные резервы. Установка для своего заказа расходует его резерв. Резервирование блокирует строку остатка на время транзакции.
- Повтор подготовки одной потребности не добавляет то же количество в заказ поставщику. Повтор приёмки не создаёт повторный приход. Для прежних потребностей сохраняется учёт уже заказанного количества.
- Добавление работы из прайса сохраняет скидку и себестоимость. Пересчёт фактических работ и деталей используется совместно основным API, складом, финансовыми покупками, инструментами собственника и прайсом.
- Зарплата, P&L и прибыль заказа используют общий расчёт с фактическим исполнителем работы. Исправлены границы месяца в часовых поясах и распределение оклада/корректировок. В прибыль включаются проведённые корректировки зарплаты; прогноз KPI сам по себе зарплату не начисляет.
- KPI открывается без персонального плана, отменённые задачи исключены из просрочки, аналитика читает действующую таблицу рекламаций.
- Гарантийный талон выпускается по событию закрытия, после выполнения условий завершения. Предоплата не активирует гарантию. Публичная ссылка проверяет действительность заказа.
- Сервисы в Docker Compose ожидают миграции основного API; складские зависимости запускаются последовательно. CI запускается также для рабочих веток feature/* и fix/*.

## Проверки

Команда из каталога `server`:

```sh
node --test test/finance.test.js test/order-close.test.js test/crm-regression.test.js
npm run check
```

24 проверки, включая групповой тест, проходят: доступ к чужим заказам, блокировка действующего токена во всех частных API, ограничения БД, штатное закрытие, документированные возвраты, повтор закупки/приёмки, резервы, скидка, единые начисления, часовые пояса и гарантия. Веб-интерфейс собирается командой `npm run build` из `web`.

Регрессии используют настоящие миграции и обработчики с PGlite и искусственными данными. Сетевые вызовы и фоновые таймеры заменены. Проверки не отправляют сообщения клиентам. Они не заменяют проверку конкурирующих соединений PostgreSQL, полный запуск Docker и ручной сценарий в браузере на установленной CRM. Эти проверки локально не выполнены: Docker в среде разработки отсутствует.

## Обновление

Перед обновлением рабочей установки сохраните резервную копию БД и вложений штатным механизмом. В PowerShell выполняйте строки последовательно, переходя к следующей только после успешного завершения предыдущей:

```powershell
git fetch origin
git switch fix/order-parts-clarity
git pull --ff-only origin fix/order-parts-clarity
docker compose up -d --build
docker compose ps
```

Нужно пересобрать все сервисы: изменения затрагивают общую авторизацию, серверные обработчики и миграцию `004-order-integrity.sql`. Миграции применяет основной API при старте. Команду удаления томов применять не нужно. После запуска обновите браузер через Ctrl+F5.

Проверьте на тестовом заказе вход сотрудника, покупку с кассой, возврат, резерв, закрытие и открытие собственником с причиной. Закрытый заказ должен отклонять обычное редактирование, а собственник должен видеть историю корректировки.

Миграция не пересоздаёт прежние финансовые операции и не меняет их суммы. Новые расчёты отчётов могут изменить отображаемые итоги зарплаты/прибыли, поскольку устраняют различия между прежними формулами. Периоды зарплаты пока не фиксируются отдельным документом закрытия.

## Оставшаяся работа по аудиту

- Шесть ролей из ТЗ: собственник, управляющий, бухгалтер, менеджер, инженер, стажёр. В этом этапе сохранены существующие OWNER/MANAGER/ENGINEER.
- Версионирование сметы и единая связь согласованных позиций с фактическими работами/деталями. Диагностика по-прежнему считает смету отдельно, завершение использует существующее сопоставление сумм; этот этап не устраняет все расхождения сметы и факта.
- Полный складской цикл: несколько резервов одной позиции, детали на руках инженера, частичные поступления и сверка исторических резервов.
- Фиксация расчётных периодов зарплаты и исторических правил начисления.
- Полный цикл рекламации, физическая выдача техники, неизменяемые версии документов и гарантийных условий, интеграции и сверка банковских выписок.
- Полный запуск сервисов, ручная приёмка по ролям и проверка восстановления резервной копии перед признанием CRM готовой к эксплуатации.
